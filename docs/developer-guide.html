Extending the Tactical Engine

Where things are, which way they point, what may not be broken, and the order to touch files in for the changes that keep recurring. Written for whoever picks up work in this repository next.

TypeScript 7 · Vite 8 · three.js 0.185 · Preact 10 · zod 4

1Orientation

Tactical Engine is a browser CRPG engine and editor for party-based tactical RPGs. A project is a JSON document — projectSchema, src/engine/scene/schema.ts:210 — holding scenes, dialogues, items, loot tables, quests, assets, abilities, code, condition definitions and the party. The engine executes that document directly; the editor writes it in the browser. There is one page, one canvas, one Preact root, and a mode switch between play and edit.

Which document covers what

Three hand-written docs, and they do not overlap. This one is the only one about extending the engine.

Where to start reading

In this order, and no further until you need it.

  1. docs/CONTEXT.md — the constraints.
  2. src/engine/script/schema.ts (1447 lines) — the effect and condition vocabulary. Everything content can say is in this one file.
  3. src/engine/script/runner.ts (1953 lines) — the stepper that runs it, and the ScriptWorld interface it runs against.
  4. src/engine/rules/damage.ts (379 lines) — the shape of a rules module: an SRD citation at the top, pure functions, an Rng passed in wherever dice are rolled.
  5. src/game/demo-scene.ts (4437 lines) — where the engine is actually wired into a playable thing; src/game/log.ts is what the player reads of it.
  6. src/main.ts (2562 lines) — the boot path. It owns the board, play and global keys (Ctrl+E, Ctrl+Z); the editor shell (src/editor/ui/EditorShell.tsx) also listens, for its own keys (1-4, Esc) and for a click outside an open menu.

2The layers, and which way they point

The engine core is a rules library. It takes plain data and an Rng, returns plain data, and mutates only what it is handed. That is what makes a fight replayable from a seed, testable in node in milliseconds, and usable on a server. Every slice so far has relied on it, so the rule is a test rather than a comment.

tests/unit/engine-is-headless.test.ts walks every non-test source under src/engine/ bar render/ and fails on an import of three, three-mesh-bvh, cannon-es, preact or @preact/signals; on any use of document, window, navigator, localStorage or requestAnimationFrame; and on any call to Math.random(). Its last case runs the checks against a deliberately bad source, so a regex that stopped matching cannot pass vacuously.

A second guard keeps files readable. tests/unit/file-size-ceiling.test.ts fails when any source under src/ or tests/ passes 1,500 lines. The files already over it are pinned at their size in the test's table, and a pin only goes down: shrink one and the test asks for the number to follow. src/game/demo-scene.ts grew from 135 lines to 5,856 in eight days before the guard existed; it is being taken apart, and the ceiling is what stops the next slice putting it back.

src/engine/render/ is the one part of the core allowed to touch WebGL, and it is a one-way adapter — scene-view.ts says so in its own comment: the engine core never knows it exists.

The one wire that runs the other way

SceneScriptWorld.spotlightSpent (src/engine/script/world.ts:263) is a callback the world holds and src/game/demo-scene.ts:810 fills in: demo.world.spotlightSpent = (id) => (demo.gmTurn?.spotlights[id] ?? 0) > 0. The world runs scripts and knows nothing about turns; the GM turn knows whose turn it is. Joining a swarm's attack is being spotlighted, so a rat that has already bitten must not bite again behind the next one — and the world cannot tell without asking.

It is a field with a default that answers false, not an import, so the core still compiles and tests on its own: a world with nobody keeping turns says nobody has been spotlighted, and everyone joins. It is the only wire of its kind, and anything that needs another should be this shape rather than an import upwards.

The game and editor split

Both sides sit on the same ProjectDoc and the same DemoScene. The game reads the document and runs it; the editor writes the document and asks the game to rebuild. buildProjectScene(project) (src/game/demo-scene.ts:759) is the seam — a real export used by the project loader, by the editor's reload and by tests alike. Export is JSON.stringify into a Blob download; import is projectSchema.safeParse then buildProjectScene, refused mid-prompt or mid-fight.

4The boot path

index.html holds a <canvas id="gl"> and a <div id="app"> and loads /src/main.ts. That file does, in order:

  1. WebGLRenderer over #gl.
  2. buildDemoScene(demoMap()) — the DemoScene: scene document, grid, state, pathfinder, party, sheets, derived characters, triggers, Rng, SceneScriptWorld, scenario state, project, snapshots, dialogues, log, pending prompt, encounter, GM turn, askDefender.
  3. AssetLibrary, then SceneView plus setDecos and syncTokens.
  4. EditorSession and EditorController over the same live project object — the editor never holds its own copy, because re-parsing would silently fork the document.
  5. PerspectiveCamera, OrbitCamera, frameCamera.
  6. Pointer and keyboard listeners.
  7. refreshPlay() renders the Preact HUD into #app.
  8. window.__engine = state — built inline at src/main.ts:1198–1565, assigned at :1565.
  9. frame(): steerCamera, view.tick, orbit.update, renderer.render, requestAnimationFrame.

The render loop lives in main.ts, not in the render module.

5The three call chains

These three are worth knowing by heart. Almost every change touches one of them.

a · A PC attacks an adversary

attackWithSelected (game/demo-scene.ts:884)
  └─ resolveAttack (engine/combat/attack.ts)          — pure, rolls and reports
       ├─ evaluateTarget (combat/targeting.ts)        — band, LOS, cover, refusal
       ├─ rollDice(profile.modifier)                  — the attack modifier's own dice
       ├─ rollDuality (rules/duality.ts)              — hit, crit, Light, Shadow, spotlight
       ├─ rollDamage (rules/damage.ts)                — Proficiency, crit bonus, flat bonus
       ├─ rollReduction (rules/damage.ts)             — the dice half of the defender's reduction
       └─ resolveDamage (rules/damage.ts)             — resistance, reduction, band, Armor Slots
  └─ afterRolled → applyRoll (combat/attack.ts)       — the roll pays out: Light, Shadow, a crit's Stress
       └─ cards on the damage roll                    — paid from what the roll just gave
  └─ landPartyAttack → applyAttack({ roll: false })   — the blow lands

There is no defence step on this side. A PC's swing is resolved without asking the creature it hits, so the defender's reduction has to live inside DamageDefenses and be applied by resolveDamage itself. That is the whole reason defenses is a field on the damage rather than a step in a pipeline, and it is the fact to reach for whenever a new "when this creature takes damage" feature needs a home.

Dice leave the stream in a fixed order — modifier dice, attack roll, damage, reduction — and a refused attack draws nothing at all, so a UI's range preview cannot shift the stream.

b · An adversary attacks a PC

playGmTurn / runGmTurn (demo-scene.ts:938, :959)
  └─ world.defenderOf(target)                          — Evasion and thresholds from the sheet,
  └─ resolveAttack  ─ rollGmDie (rules/gm-die.ts)        plus whatever the conditions add
       ├─ miss  → applyAttack at once, then offerMiss  — a card may answer a miss
       └─ hit   → offerOrLand (demo-scene.ts:1643)
            ├─ askDefender and more than one choice → demo.pending = a defence prompt
            │     defenseChoices (:1538) labels them with previewPlan (combat/defense.ts)
            │     applyDefenseChoice (:1718) → landAttack with the chosen DefensePlan
            └─ otherwise → landAttack (:1670) with plan = null
                 plan === null → world.defend → resolveDefense   (the engine decides)
                 plan !== null → resolveDefensePlan               (the player decided)
                 then applyAttack against a rebuilt AttackOutcome

Once the blow is resolved, whoever it happened to gets to answer it. playDamageReactions drains the notes and reads them for both sides: a stat block's reactions run on their own, and so does a party card that costs nothing and asks nothing (Rise Up's “clear a Stress”). A card with a price — “you can spend 2 Light to…” — is put to the player as a third kind of demo.pending, a PendingReaction, whose first option is always letting it pass. The line between the two is auto and no cost: a card that should be asked about anyway sets auto: false. A swing at somebody also raises attacked on them, hit or miss, which is how a bonus that lasts “until after the next attack made against you” knows when it is over. A roll the party makes raises partyRolled on every adversary standing: the one who rolled is bound as the target, so the distance is a plain withinRange, and what the dice said is a rolled condition — the five readings compose, so “a failure with Shadow” is an all of two. The same happens on the party's own swing: playAttackRiders reads dealtHit and dealtDamage for whoever swung, so Healing Strike is offered after a player's attack the way a stat block's rider runs after the GM's. Every note is read before anyone is asked, because drainDamage clears as it reports; what is not asked now is queued behind the question that is up.

Both defence functions use the same arithmetic in the same order: dice off the damage — a Rune Ward's d8, and the passive reduction, rolled once — then Armor Slots, the one plus any an extraArmor reaction adds, then the band stepped down by reduceSeverity reactions.

resolveDefense weighs each up and spends nothing that would not lower the Hit Points marked. resolveDefensePlan obeys instead: a Rune Ward the player asked for is rolled and paid for even when the die comes up short, which is what happens at a table. previewPlan rolls nothing and returns null whenever an honest answer would need dice — for a reduceDamage reaction, and equally for a defender whose own passive reduces by dice.

c · An ability is played through the script runner

AbilityDef.effects  (content/abilities.ts, shapes from script/schema.ts)
  └─ new ScriptRunner(world, rng, { targets, hit, subject, rollAs })
       run(effects) → step() → apply(effect)          — one switch, no default
            ├─ instantaneous effects journal and return null
            ├─ branch / choice / check / attack / reactionRoll push a Frame
            └─ choice and check return a Prompt        — the runner stops
       caller answers with resume(response)            — 'choose' | 'roll' | 'continue' | 'cancel'
  └─ SceneScriptWorld (script/world.ts)                — the only writer of state
       dealDamage → defend → resolveDefense
       attack     → builds an AttackProfile, then resolveAttack + applyAttack
       hooks (script/hooks.ts) queue more effects; they never write
       countdown arms a clock on the scenario; the game layer ticks it
       spotlight journals who the GM turn was handed to; the game layer queues them
       replace takes the actor off the map and stands another stat block there
       move walks the actor across the ground: towards somebody, or away from them
  └─ JournalEntry[]                                    — what happened; the log renders it,
                                                         a test asserts on it

The bindings the runner carries: targets, whom the player picked; hit, whoever the last roll beat; lastRoll, for a critical's extra dice and difficulty: 'roll'; and lastDamage, for dice: 'same'. A Frame may carry its own hit, so a reaction roll's failures and its successes each read the right list however the next roll goes.

A passive can change the block's own teeth rather than a number on it: standardAttack carries direct, damage (dice instead of the printed ones) and double, each under an optional when read from the attacker's chair with the target bound — so “while Hidden” is a hasCondition on the actor and “against a PC with 0 Light” a pool on the target. Doubling happens once the dice have settled, so a bonus doubles with them and the thresholds read what actually landed.

A modifier can count as well: perToken multiplies the whole bonus by the tokens sitting on a card, so “a +5 bonus to your damage roll for each token on this card” is one modifier and an addToken that places them. Tokens are scene state, so a perToken modifier is deliberately left out of deriveCharacter and read where it is used, every time.

A stat block can keep a count on itself the same way. The token store is keyed by creature and card, so nothing says a card has to be one a player holds: the four Slow blocks share one spotlighted reaction that branches on its own tokens, placing one on the turn the creature gathers itself and spending it on the turn it acts. What pays for the wait is endSpotlight, which does not stop the script — the effects after it still run — but tells the GM's turn that this creature is done: no feature, no swing, not even shaking off a hold. Anywhere but a spotlighted reaction on a stat block it is a silent no-op, and the validator says so.

The other way round is spotlightAgain: the creature acting goes back to the head of the GM's queue, granted, because whatever said so has already paid for the turn. That is the Construct's Overload — a Stress buys ten damage and another spotlight — and it is read where every other spotlight entry is read, once the script is done, so the blow it is standing over lands first. A stat block with a Relentless spotlight still coming is filtered out of the queue before it is put back, so it stands there once.

A wound is heard three ways. tookDamage is the one who took it, allyTookDamage is everyone on their side, and nearbyTookDamage is everybody else in the room whichever side they are on — the Shark smelling blood. For the last one the dealer is bound as the target and the wounded as the hit, so a feature can ask how far away either of them is: Close range to the blood is not the same question as Close range to the knife.

One blow stops the fight outright: the one that marks a character's last Hit Point. The SRD makes that a decision — a death move — and it is the only question in a fight the engine cannot answer for the player, because two of the three answers put the character back on their feet. Avoid Death drops them unconscious, which is what a fallen character already is here, and rolls the Light Die against their level for a scar; a scar crosses out a Light slot on the sheet for good, and the fight after this one starts a Light short. Blaze of Glory takes one final swing at the nearest adversary still in reach, which does not roll at all — it automatically critically succeeds — and then they cross through the veil. Risk It All rolls the Duality Dice with nothing to beat: Light high and they stay up clearing the Light Die's worth, Shadow high and they do not, matching and they stand with nothing marked. The question is asked before anybody counts who is left standing, which is why a lone character who risks it and wins is still in a fight that is going on.

One card answers that question instead of answering it with a move: Unbreakable, which clears a d6 of Hit Points and then goes to the vault. It is offered inside the same prompt, after the three, because “instead of making a death move” is a fourth thing to choose rather than a question asked before the choice; a card that is played and leaves the character on the floor has spent itself and bought nothing, so the three moves are put again without it. The trigger is defeated, which a stat block already uses for the last thing it does. vaultCard is the effect that spends it: six of the SRD's cards end with “then place this card in your vault”, and for three of them that is the only cost they have. The script does not know which card it is running, so the effect raises a flag on the runner and whoever ran the card takes it out of the loadout — after which the Recall Cost is the way back.

A card can be aimed at the ground. Every selector until now measured a band around a creature, so nothing the SRD writes as “to a point within Far range” could be said at all — Deathrun, Salvation Beam, Zone of Protection, Eclipse, and the gallop-in-a-line features four stat blocks print. An ability says target.kind: 'point'; the bar arms for tiles rather than creatures; the tile comes down the same channel the targets do, as bindings.point. Three shapes read it. inPath is everything the straight line from the actor to that tile runs through — traced with the same walk sight uses, so a charge and a look down a corridor agree about what is on it — and around: 'point' on allies and adversaries measures the band from the ground rather than from whoever happens to be standing on it. The one charging is never caught by their own run; somebody standing on the spot being run to is.

The board draws it before the click. shapeAt asks who a card aimed at a tile would catch, against a world nothing has changed, so the answer can be recomputed on every pointer move and lit up under the cursor. A spot behind a wall is a legal thing to aim at — “a point within Far range” is a place in the room — and the run that follows still only goes where the ground allows. On the GM's side there is nobody to click a tile, so a stat block's charge runs at the nearest party member: the same rule its swing already uses to choose whom to hit.

A swing that misses stops too, on dealtMiss. It is the other half of dealtHit and not the same thing as attackMissed, which is a swing that missed you; this one is your own that went wide, with whoever you swung at still bound as the target so a card can reach them anyway. It is raised before the turn is spent, because a miss hands the spotlight to the GM and a question left on the far side of that is one the player answers on somebody else's turn.

Three smaller things a card can now say. maxOneDie is Versatile Fighter's “the maximum result of one of your damage dice”: it journals and does nothing, because the faces a swing came up are not something a script can see, and the blow being held does the arithmetic — the lowest die goes to its highest face, which is the one anybody would pick. reach: 'weapon' on the adversaries selector is “within your weapon's range”, whatever the actor is holding, with the named band standing in for anyone holding nothing the engine can read. And nearest on the hit selector is “choose one of these targets”, picked the way every other automatic choice here is.

A reaction's blow can be the one that ends a fight, and a reaction is neither an act nor a spotlight — which are the only two things that count who is left standing. So settling a blow asks the encounter outright once there is nothing left to answer. The order matters: the death move goes first, because two of the three moves put the character back on their feet and the fight must not be called over their head.

A blow stops once between landing and being counted. rollingDamage is raised on the creature swinging and allyRollingDamage on every other adversary still standing, both with the one being hit bound as the target — so “within Far range of the Turret” is a plain withinRange from the reactor to the defender. What they add is boostDamage: a flat amount, dice to roll, or dice: 'weapon' for the reactor's own printed attack, rolled times over when the count is something the fight decided — “roll the dice on this card” is one d8 rolled once for every token on it. Like endSpotlight it journals rather than writes; the game layer sums what the moment reported and adds it before the defence, so thresholds and Armor Slots read what actually arrives. Only the GM's own swing raises it — a scripted attack inside a feature keeps its outcome inside the world.

The one thing a card can say at that moment which is not a sum is forceHitPoints: “force the target to mark a number of Hit Points equal to the number you currently have marked instead of rolling for damage”. It names Hit Points rather than damage, so nothing stands between it and the target — no threshold, no resistance, no Armor Slot — and the dice the attack already rolled are thrown away. It wins over anything added to the same blow, because a blow that is not being rolled for cannot be added to. Only the party's own swing obeys it today; the validator warns on a stat block and outside rollingDamage.

Its softer sibling is forceSeverity, which names the band rather than the Hit Points: “spend a Shadow to deal Severe damage instead of their standard damage”. A band is not a number of marks, so the defender's Armor Slots still step it down the way they step down a Severe hit that was rolled for — what they cannot do is take damage off a total, because there is no total left. Both sides of the fight obey it, and a stat block can also name a band without a reaction at all: standardAttack.severity is read off the block with the target bound, which is how the Seraph's Judgment strikes at whoever carries its mark. Underneath both is one field, IncomingDamage.severity, which resolveDamage uses in place of reading the thresholds.

A band can also be a floor rather than a swap: forceSeverity with least counts the blow as it was rolled — resistance, thresholds, whatever armor answered with — and lifts it only if it came out under the band. That is Onslaught's “you never deal damage beneath a target's Major damage threshold”, which is about what the target marks rather than what the attack rolled, so it is read after the counting rather than instead of it. The party's swing obeys a floor; a stat block's does not, and the validator says so.

Severe is a floor, not a bracket. “When the Burrower takes Severe damage” answers a Massive blow too, so every place that reports a wound asks isSevere rather than comparing to the one band.

The party's swing stops at the same moment, and this is the one place a prompt sits between a roll and its counting. A card on rollingDamage is offered after the attack has hit and before anything is marked; the swing is held on the pending question as data (the same way an incoming hit is held while its defender decides) and lands once the question is done with, whichever way it was answered. A blow that grew is counted again from the top — thresholds, resistance, Armor Slots, and the defender's own reduction rolled afresh — because what the attack rules resolved was the smaller number.

Not every card at that moment is a question. One that costs nothing and asks nothing runs where it is found, inside the offer step, and what it said about the blow has to reach the caller still holding it: the held swing travels into that step in a box, and is folded with whatever ran on its own before the blow is either put to the player or landed. Without that, a card rolling dice it had collected would write its total to the log and nowhere else.

The defence step answers a blow with shapes — reduceDamage, extraArmor, reduceSeverity, redirect, reroll — because every option it offers is previewed with the Hit Points it would cost. A card whose answer is a script cannot be previewed, so it is offered on its own, without a number, next to the plans: softenBlow takes what it rolls off the blow, and avoidBlow means the blow arrives and finds nobody. Both journal rather than write, and the game layer folds them the way it folds a boost mid-swing — softening comes off the total the swing rolled, so the thresholds and the Armor Slots read what actually arrived.

Two things follow from that shape. The blow is put to the defender again once the card has been played, with the card's id in used: marking an Armor Slot and playing a card are both answers, and the SRD lets somebody give both. And an avoided blow is neither a hit nor a miss — the attack roll succeeded and then found nobody — so the swing is spent, nothing is marked, and the riders that answer a landed blow never run. A card that stops to ask something of its own holds the blow while it asks, exactly as the party's own swing does.

Two more words belong to that moment. stepSeverity takes the blow down a band after the armor rather than instead of a slot, which is what a card paying for something the armor did not do actually says; the landing applies it to the resolved band and reads the Hit Points off that. dodgeBy is stranger: it raises the Difficulty the swing was already rolled against and measures the d20 again, so a blow that had landed may not have. A natural 20 is past arguing with, and a bonus that was not enough changes nothing at all — which is the card's own bargain, since the Stress is spent either way.

Some cards ask a question the dice answer: “roll a number of d6s equal to your Proficiency — if any roll a 6”. diceCheck is that shape: dice rolled times over, needed of them showing atLeast, then one of two lists. Every card that asks it counts out a different pile — one per Light spent, one per point of Proficiency, one per token — so times is an amount like any other, and proficiency joins the traits an amount can read. No dice at all is not a failed roll: otherwise runs and nothing is journalled, because a holder who spent nothing has not rolled and lost.

A card can ask what the dice said. rolled has always been able to read a roll — it is how a stat block answers “when a PC rolls a failure with Shadow” — but the moment a swing lands carried no roll with it, so a card asking “when you critically succeed on an attack” read nothing and never fired. The roll now travels with the offer: into the gate that decides whether the card is offered at all, and into the script it runs, so an effect can branch on it as well. Four cards were waiting on that one binding.

The other side of a wound has a trigger of its own. tookDamage is the one who was hit; allyTookDamage is everyone else on their side, raised with whoever dealt it bound as the target, which is how a card set on one creature counts what that creature does to the whole party. It is the pair of allyRollingDamage and split from tookDamage for the same reason: a card that answers its holder's own wound must not answer every wound in the party.

An amount can be read off a sheet as well as off a pool or a card: { trait: 'strength', times: 2 } is “equal to twice your Strength”, trait: 'spellcast' is the one the holder casts with, and trait: 'proficiency' is the number their weapon multiplies by. A creature with no sheet — every stat block — reads it as nothing rather than refusing, which is the same quiet zero a pool nobody has gives.

A condition can count creatures, too. The selectors already say which ones and where — around the actor or around the chosen target, off the same stat block, everyone but the one asking — and nearby asks how many there are: “another Dire Wolf is within Melee range of the target” is that selector and >= 1. A creature is within Melee of itself, so anything counting its own kind wants except: 'actor'.

An ability can also say what makes a creature worth aiming at. target.when is read once for each candidate, with that candidate bound as the target, and it narrows both lists that matter: the creatures a player may click, and the ones the GM will spend a Stress on. That is what keeps a feature reading “a target with 3 or more bramble tokens” from being paid for and aimed at somebody carrying none.

Some cards ask the player for a number rather than naming one: “spend any number of Light to roll that many d6s”, “transfer any number of their marked Stress”. howMany is that question. It says the most that can be asked for (a number, a pool, or tokens on a card), the least that may be answered, and each — what one of them does. It asks; it does not pay: what the number costs is written in each, the way the card's own words write it.

The answer arrives by substitution, not by binding. For every number the player could give, a copy of each is made with 'spent' (wherever an amount is written) and {n} (wherever dice are) replaced by that number, and the whole thing is pushed as an ordinary choice. So anything that can draw a choice can draw this, nothing downstream has to know where the number came from, and the two words mean nothing outside a howMany — which the validator says out loud.

An amount can also be read off somebody's pool: { pool, of, measure }, or off the tokens on a card ({ tokens, of }). The pool read uses the same three words the pool condition asks with, so a feature's gate and its amount read one number. of is the actor when left out and measure is what is marked, which is what “a bonus equal to the Demon's current number of marked HP” means. A pool on nobody is a quiet zero rather than a refusal, the same as an empty count.

It carries numbers as well as creatures. Wherever an amount is written — damage.amount, markStress, clearStress, heal, loseGood, gainBad — a count may stand in its place: hitPointsTaken, the Hit Points the blow that called for this script marked on whoever is answering it; hitPointsDealt, what this script's own damage has marked; targetsHit, how many creatures its last roll beat. A count condition compares one, so a feature's available gate and its effects read the same numbers — "when the Brawler marks 2 or more HP". A count nobody seeded is zero, and a zero does nothing quietly rather than refusing. Damage is never a count: "half the damage they dealt" is dice: 'same' with half, which keeps the blow's own dice and type and goes through thresholds the way the original did.

The awkward part of scripting a CRPG is that most effects are instantaneous and a few need the player. The legacy prototype solved that with await all the way down, which pulled the DOM into its rules and made a scenario impossible to test or replay. The stepper is the answer to that, and it is why the whole layer runs in node.

6The key types

Two pairs of names collide; keep them apart. Condition (script/schema.ts) is a predicate; ConditionDef (content/conditions.ts) is a status on a creature. And DefenderProfile (combat/attack.ts) is the target as an attack sees it, while Defender (combat/defense.ts) is the target as a defence sees it — different types, different files, different jobs.

7The project document

Almost every array is .default([]), deliberately: a project written before quests, abilities, code, conditions or an authored party existed is still a valid project. The exception is scenes, which is .min(1) — a project with no scene is nothing to play. formatVersion is 3: an older file is migrated as it is read, and one from a newer build fails at the door rather than half-loading.

8Invariants

Each of these exists because breaking it once already cost something. They are rules, and each carries its reason.

One effect and condition vocabulary, and never a second

src/engine/script/schema.ts is the only place either union is declared. There were once two: a nine-variant one in scene/schema.ts that a document could hold, and the full union in effects.ts that the runner could execute. Nothing converted between them, so an interactable's authored check was imported, validated, saved — and never run. scene/schema.ts, dialogue/schema.ts and content/abilities.ts all import from script/schema.ts now. A converter would be a second vocabulary to keep in step and the obvious place for the two to drift; add a variant to the one union instead.

The engine core stays headless

No DOM, no WebGL, no three, no preact under src/engine/** outside render/. It is what makes the rules testable in node, replayable from a seed, and runnable without a browser. A single stray import would not fail a test on its own, which is why tests/unit/engine-is-headless.test.ts exists to fail it.

Every roll comes from a seeded Rng; nothing in src/engine/** calls Math.random()

A run is reproducible from its seed, so a test pins an exact outcome and a save restores the stream position. Project code cannot escape it either: script/hooks.ts shadows Math with SAFE_MATH, whose random throws "Math.random is not available in a hook: roll off ctx.rng so replays stay in step", and shadows Date so a stray Date.now() is a TypeError the author sees at once.

Content ids are stable kebab or snake case; never rely on array order

contentIdSchema in scene/primitives.ts is /^[a-z0-9]+(?:[-_][a-z0-9]+)*$/, and toContentId() in content/types.ts normalises a display name to it. Array order changes whenever someone reorders a list in the editor; an id does not.

A project's content lays over its pack's by id, whole

mergePack (content/pack/import.ts) lays a project's lists over the pack's: an entry with a pack entry's id replaces it entirely — not a field-by-field merge — and the pack's other entries survive. The Cards panel's Edit a copy is this on purpose: the copy of a pack's card it adds to the project is the card played, and Remove copy (removeCard) takes it out again. Which of a project's cards are copies is the shipped pack's to say, so the panel is handed that pack before the project is laid over it (characterPack) as well as after. What a project places is what it carries: a stat block brings no scripted feature with it unless a pack or the project prints one on it.

Importers never throw

A broken entry is skipped and reported as a ContentIssue, so one typo cannot take down a whole project. Anything arriving from outside the process — a save file, localStorage, an imported project — parses through a zod schema at the door, so a corrupted file fails loudly there rather than as a crash three moves into play.

Optional rules stay opt-in

Massive Damage (SeverityOptions.massiveDamage) is off by default because the SRD prints it as optional, and the critical-damage rule is a flag (criticalRule: 'maxDicePlusRoll' | 'doubleDice') because the community summary contradicts both official versions. Neither becomes the default without a citation.

applyAttack reports what actually happened

Not what was asked for. Light at its cap does not accrue; a target with one Hit Point left marks one however severe the hit was. Anything that reads the result reads the truth, which is what lets a log, a save and a test all read the same value. applyRoll is its first half on its own: a caller that stops between the roll and the blow settles the roll there and lands the blow with roll: false, so nothing is paid twice.

9Recipes

Four changes that keep recurring, in the order the files must be touched. Each is derived from a commit that did exactly this.

a · Add an effect to the script vocabulary, end to end

Worked example: loseGood — the engine side in commit 8c80bc2, the editor row in d19c101.

  1. src/engine/script/schema.ts — add a variant to effectSchema's discriminated union, with a doc comment giving the SRD sentence it answers and how it departs from it. If it nests effects, use zod 4's getter form (get onHit() { return z.array(effectSchema).optional(); }) and add the descent to walkEffects; if it holds a condition, add it to walkConditionsIn. A walk that forgets to descend reports a clean bill of health for a broken file.
  2. src/engine/script/runner.ts — three edits in one file: a method on the ScriptWorld interface if the effect needs the world to do something new (loseGood(id: string, amount: number): number); a JournalEntry variant for what it did ({ kind: 'goodLost'; lost: number; id: string }); and a case in the apply switch at runner.ts:549. The switch has no default, and apply returns Prompt | null, so a missing case is a tsc --noEmit error — that is the check that a new variant was actually wired up.
  3. src/engine/script/world.ts — implement the method on SceneScriptWorld. It is the only writer of state; nothing else may reach into an EntityState.
  4. src/editor/ui/EffectList.tsx — add the kind to ADDABLE, a human label to the label map (loseGood: 'Take their Light'), a case in the row renderer and a case in the default-value builder. The panel shows what it cannot build rather than hiding it, so this step can lag the engine by a commit — but it must land, or the effect exists and nobody can author it.
  5. src/editor/validate.ts — if the effect names content that must exist, or holds a string that must parse, report it there. Saying so while it is being written beats saying so when someone reaches for it.
  6. Tests. src/engine/script/runner.test.ts for the stepper's handling, src/engine/script/abilities.test.ts for it inside a real card, src/editor/ability-edits.test.ts for the panel writing it, and tests/e2e/demo.spec.ts if a person has to be able to click it.
  7. Docs. docs/MANUAL.md gains the row in the effect table. If the effect lets a card the starter pack ships as text be scripted, script it in src/engine/content/pack/starter-abilities.ts.

A second worked example, and the most recent. attack.joinedBy, with sameKind on the adversaries selector, commit 058c3af: a Minion swarm walks into reach and swings on one roll, the damage counted once for each body standing there when it lands. It is a field on an existing effect rather than a new kind, so there is no new case in the switch and no new JournalEntry; it went schema.ts → runner.ts → world.ts → EffectList.tsx → tests → the docs, which is steps 1, 2, 3, 4, 6 and 7 above, in order. Step 5 was skipped because the field names no content that has to exist. One field scripted Group Attack on sixteen stat blocks, which is the shape to aim for: a feature printed many times with one number changed is one field, not sixteen entries.

b · Add a field to AbilityDef

Worked example: defenses.reduce, commit 6ec74ef — "a number off the damage before the bands". Eighteen files, one sentence of rules.

  1. Decide where it is read first; that decides the design. A PC's swing at an adversary is resolved in resolveAttack and applied at once, with no defence step to catch it. So reduction went into DamageDefenses and resolveDamage does the flat half itself, which reaches every path damage takes without asking a caller for anything.
  2. src/engine/rules/damage.ts — the rule. DamageReduction, flatReduction, reductionRolls, rollReduction, ResolveDamageOptions.rolledReduction, and the arithmetic in resolveDamage. Comment the order you picked and why: resistance halves first and the number comes off what is left, because no SRD block has both and the order was ours to choose.
  3. src/engine/content/abilities.ts — the content side: the field on damageDefensesSchema, with the SRD sentence it answers in the comment.
  4. src/engine/combat/attack.ts — roll the dice half once per swing and hand it to resolveDamage.
  5. src/engine/combat/defense.ts — the same, once per hit, in resolveDefense and resolveDefensePlan; and make previewPlan return null when an honest answer would need dice.
  6. src/engine/script/world.ts — collect the field off everything the creature holds. defensesOf reads passives and active conditions; resistances and immunities dedupe, reduce entries stack.
  7. src/game/log.ts — say it. A hit for 11 that marks nothing looks like a bug otherwise, so reduced travels in the journal entry on every path damage takes, and describeEntry prints it.
  8. src/editor/ui/AbilityPanel.tsx — a row for it (data-testid="ability-reduce", ability-reduce-type).
  9. src/editor/validate.ts — refuse what would silently do nothing. Here: a reduction that is not dice, and a reduction whose modifier is negative, because "1d10-2" would hand the attacker two damage back.
  10. tests/fixtures/adversary-features.ts — a specimen that carries it, printed on a block with printed(blocks, feature): here PLATE_THAT_TURNS_A_FLAT_AMOUNT and PLATE_THAT_ROLLS_WHAT_IT_TURNS.
  11. Tests: rules/damage.test.ts, combat/defense.test.ts, editor/validate.test.ts, editor/authored-scenario.test.ts, and a line in tests/e2e/demo.spec.ts.
  12. The prose in docs/MANUAL.md and docs/CRPG-GAPS.md.

c · Script a stat block's feature

A stat block's feature is content, not engine code: the engine ships none — the starter pack's creatures carry printed traits only — and a pack or a project brings its own.

  1. Trait or feature? Relentless, Horde, Minion, Momentum and Terrifying are read structurally off the block (combat/adversary-features.ts, IMPLEMENTED_FEATURES): a trait belongs there, as a rule the fight obeys. Anything the GM plays is a feature, and is scripted.
  2. A card printed on the block, and the ability on it. In cards, a card whose grant is { kind: 'adversary', adversaries: [...] }; in abilities, the feature with source: { card }, text as printed, kind, cost (Shadow is the GM's pool), target, inCombatOnly, and effects in the one vocabulary. In the editor, write it in the Cards panel and set granted by to stat blocks. Comment every departure from the printed text next to the thing that departs.
  3. If the vocabulary cannot say it, add an effect (recipe a) or write it as code the pack carries (code, reached by a run effect). If you do neither, leave the feature as text for the GM to narrate — an unscripted feature is honest; a half-scripted one is not.
  4. src/editor/validate.ts already knows what only a stat block may do and what only the party's own swing obeys; isStatBlockFeature asks the cards, and a new rule of that kind asks the same question.
  5. Test it on a fixture block. Write the feature once in tests/fixtures/adversary-features.ts and print it with printed(blocks, feature); print(project, ...) lays card and ability into a project. Play it in src/editor/authored-scenario.test.ts or src/engine/script/abilities.test.ts and assert on the journal.

d · Add a condition (a status on a creature)

There is no editor panel for conditionDefs — a project carries them in its JSON, and a pack carries the ones its cards and stat blocks apply. The engine ships only the three its own rules read.

  1. Beside whatever applies it — a project's conditionDefs, the starter pack's src/engine/content/pack/starter-conditions.ts, or an imported pack's conditionDefs: id in kebab case, name, text, and then whichever of modifiers, defenses, blocks (act / move / reactions) and endsWhen (hit / attacks / damaged) it needs. RAW in src/engine/content/conditions.ts is only for a condition the engine's own rules name.
  2. Only if the attack roll itself must change: src/engine/combat/attack.ts:conditionModifiers. It hard-codes exactly two — vulnerable gives advantage against the bearer, hidden gives disadvantage — because those are the two the SRD puts on the roll. Everything else a condition does belongs in modifiers or defenses, which world.modifiersOf and world.defensesOf read.
  3. src/engine/script/world.ts — nothing, normally. applyCondition, clearCondition, blocks, endsOnHit, endsOnAttack and endsOnDamage are already generic over the definition.
  4. Duration. A script applies it with { kind: 'applyCondition', condition, duration }, where duration is temporary, scene, rest or permanent. A temporary condition on the party is cleared once per GM turn inside playGmTurn, past its guards, so it happens however the spotlight passed — which means a beneficial condition must be scene or rest, never temporary.
  5. src/editor/validate.ts — condition ids named by an effect are checked against project.conditionDefs (validate.ts:169 and :240). A new shipped condition needs nothing there; a new field on ConditionDef may.
  6. Tests: src/engine/script/conditions.test.ts and src/engine/script/abilities.test.ts.

10Testing

Where a test goes

A co-located *.test.ts next to the module is the default — every module ships with one. tests/unit/ is for tests about the repository rather than about a module: the headless guard, the whole-SRD import check, the demo scene, the demo fight, the legacy campaign import, and the toolchain spike. tests/e2e/demo.spec.ts is for anything that needs a browser, a canvas or a click.

npm test                       # vitest run — 70 files, 1205 tests, ~6s
npx vitest run <path>          # one file, while working
npm run typecheck              # tsc --noEmit — the only static check there is
npm run test:e2e               # playwright, 52 tests in one file; slow
npm run check                  # all three

Vitest's include is tests/unit/**/*.test.{ts,tsx} and src/**/*.test.{ts,tsx}, environment node, globals: false — import describe, it and expect from vitest explicitly. happy-dom is available for a DOM test but is not the default.

Seeded-RNG discipline

Never Math.random(), and never a bare createRng() where the outcome matters. Either pin a seed (createRng('demo')) or hand the rule a scripted double.

The double is declared locally in each test file that needs it, not shared: as scriptedRng(faces) in combat/attack.test.ts, rules/duality.test.ts, rules/gm-die.test.ts, script/runner.test.ts and dialogue/dialogue.test.ts, and as scripted(values) in combat/defense.test.ts and script/abilities.test.ts. It returns the given faces in order and throws scriptedRng exhausted after N draws when over-consumed — which is itself an assertion. A test that hands the runner exactly one die proves the code rolls it exactly once; c9fdecc used that to prove the script attack path does not roll a defender's reduction twice.

Other per-file helpers by the same convention: scene(seed) wrapping buildDemoScene, and standoff(seed) in src/game/demo-defense.test.ts, which builds a fight already holding a pending defence prompt.

The e2e handle and the selectors

window.__engine is built inline in src/main.ts and assigned at :1565. It exposes what a test cannot get at through the DOM: frames, webgl2, errors, tiles, entities, decos, missingModels(), party(), selected(), select(id), selectNext(), tileOf(id), inCombat(), round(), adversaries(), hitPoints(id), moveTo(tile), attack(id), endGmTurn(), highlighted(), reachable(), sample(x, y), setMode(mode) and exportProject(). sample re-renders inside the same task before reading pixels, because the drawing buffer is not preserved between frames. A spec waits on (window.__engine?.frames ?? 0) > 5 before touching anything.

data-testid is kebab-case prefixed by the owning panel — ability-name, item-kind, code-source, check-difficulty. Actions are add-<thing>, open-<panel>, close-<panel>, and row ids interpolate the content id. There are 124 of them across the panels. Prefer a testid over a text selector for anything the copy might change, and getByRole('button', { name }) for anything a player reads.

A regression test must be shown to fail without its fix. Writing the test after the fix is not enough — a test that passes both ways proves nothing. Revert the fix (stash it, comment the line, git checkout the file), run the test, watch it fail with the message you expect, restore the fix, run again. Then say so in the commit body, naming which way it fails. 6ec74ef records that its content test fails both ways: without the roll in resolveAttack the dice half does nothing, and without defensesOf collecting the field the flat half never reaches the defender.

11The working loop

A slice

One behaviour, complete: the rule, the content that uses it, the editor field that writes it, the validation that refuses it when it is wrong, the tests that pin it, and the docs that describe it. Not a layer at a time. Look at 6ec74ef — eighteen files, one sentence of rules. A slice that adds an engine capability with no way to author it, or a panel field nothing reads, is half a slice, and will be finished by someone with less context than you have now.

The verification line

Every commit body states what was run and what came back:

`npx tsc --noEmit` clean, 1205 unit tests across 70 files and 52 e2e pass.

Then a sentence on how the new tests were shown to fail without their fix. If something could not be verified, say that instead of implying it works.

The message and the trailer

The subject is a sentence about the behaviour, not about the files: "Let a stat block wear plate: a number off the damage before the bands". The body explains the design decision and why the alternative was rejected. The trailer:

Review, then follow up

A slice lands, a review reads it, and what the review found lands as its own commit that says so — c9fdecc opens "Follow-up to the reduction slice, from review". Three of the last four commits are that pattern. Do not amend the reviewed commit; the pair is the record of what was missed and what caught it.

12Content and licensing

Where content comes from

Nothing is vendored. The engine ships its own starter pack (content/pack/starter.ts, with starter-abilities.ts and starter-conditions.ts), nobody else's content, and reads anything else as a pack a user imports — Project ▾ → Import pack…, through content/pack/document.ts. The SRD catalogue this repository once carried was exported before it was deleted; docs/CONTEXT.md says where, and why the export is git-ignored.

Where the rules come from

The SRD 2.0 text, as settled while it was here. The section-by-section diff against 1.0 is recorded in docs/CONTEXT.md, which is now the reference for what the engine implements and why. One number is a choice the engine exposes rather than a quotation: critical damage adds the dice's maximum, as both SRD versions say, and a table that doubles the dice instead can set criticalRule: 'doubleDice' — rules/damage.ts says so above the flag.

13Gotchas

  • The repository path contains a space. Quote it everywhere. The repo has moved between machines before, so prefer repo-relative paths in code, scripts and docs, and never hardcode a path or a home directory.
  • legacy/ is never modified. It is the original prototype, kept runnable via legacy/start.bat. It also serves on port 8420, so do not run it and npm run dev at once. Read docs/research/legacy-*.md rather than the sources.
  • Ports. Vite dev and preview on 127.0.0.1:8420; Playwright starts its own on 8421 with --strictPort, and reuses an existing server if one is already there.
  • There is no lint and no format tooling. No ESLint, no Prettier. npx tsc --noEmit is the only static check, and it is strict with noImplicitOverride, noFallthroughCasesInSwitch and isolatedModules. Match the surrounding style by reading it.
  • grep sees some sources as binary — src/game/demo-scene.ts among them. Pass grep -a, or the match count comes back as "Binary file … matches".
  • Path aliases: @engine/*, @editor/* and @game/* resolve. @content/* points at content/* and there is no content/ directory at the repository root — it is a dead alias, imported nowhere. docs/CONTEXT.md lists all four without qualification. Content lives in src/engine/content/ and in the project document.
  • fflate is a dependency and is imported nowhere under src/. CONTEXT.md's "zip import and export of projects with assets" is not implemented; export is JSON.stringify into a Blob.
  • No frustum culling and no LOD. Instancing and geometry sharing exist (terrain-mesh.ts, and procedural/build.ts with its PrimitiveCache and MaterialLibrary); the rest of the efficiency goals in CONTEXT.md are stated, not met. docs/CRPG-GAPS.md is the honest list.
  • No TTS, no speech synthesis, no "voice" features. A hard constraint from the user; both previous attempts were removed.
  • All content text is English.
